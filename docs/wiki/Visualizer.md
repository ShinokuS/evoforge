# Z-level Visualizer and Procedural Landscape

The EvoForge visualizer is a **debug observer of the real simulation**, not a second world model and not an owner of simulation state.

Its presentation contract is **full top-down with a true horizontal Z cut**. Landscape art is generated by EvoForge itself at startup instead of depending on an external tileset.

## Module boundary

```text
simulation  pure Java, authoritative and headless
    ↑
core        libGDX presentation/debug visualizer
    ↑
lwjgl3      desktop launcher
```

`core` depends on `simulation`. `simulation` has no dependency back on libGDX, pixels, palettes, atlases or presentation code.

`SimulationAssembly` builds the initial world and `start()` returns `SimulationRuntime`. The visualizer receives only:

```text
SimulationView
SimulationTime
SimulationStepper
```

It never receives `SpatialSystem`, `TerrainSystem`, `GeometrySystem`, `MovementSystem`, `Scheduler` or `SimulationClock`.

## Selected Z means a horizontal cut

Visualizer Z is the **standing/navigation plane**, because Spatial objects and Navigation transitions live at that coordinate.

Under the current supported-position Shape law, terrain/Shape supporting standing position `(x,y,z)` is anchored at:

```text
(x, y, z - 1)
```

The renderer no longer treats a selected level as an isolated floor with a transparent lower floor. For every visible XY it resolves a horizontal cut in this strict order:

```text
1. terrain anchored at selected Z
      -> SOLID BODY intersecting the current slice

2. otherwise terrain anchored at selected Z - 1
      -> CURRENT SURFACE supporting this standing plane

3. otherwise search downward through the open column
      -> nearest LOWER SURFACE within the configured depth

4. otherwise
      -> EMPTY
```

This contract is implemented by `LandscapeSliceResolver` and is headless-testable independently of libGDX.

### Why solid body has priority

A higher plateau must not disappear when the user switches one Z level down.

Example:

```text
standing Z=1      grass top
                  ─────────
terrain Z=0       █████████  solid material
standing Z=0      horizontal cut through that material
terrain Z=-1      lower support
```

When selected Z is `1`, terrain at `0` is drawn as the current walkable surface.

When selected Z is `0`, that same terrain is not a ghost floor above. It occupies the selected spatial slice and is drawn as procedural earth/rock cut material.

This makes mountains shrink/grow naturally as the selected cut moves through their stacked terrain cells.

## Open columns and lower depth

Lower context is visible only through a genuinely open vertical column.

If neither solid body at selected Z nor support at selected Z-1 exists, the renderer searches downward for the nearest surface. The first found surface is drawn with depth-dependent dimming.

Current debug depths are:

```text
0   current cut only
1   one lower standing elevation
4   up to four lower standing elevations
```

`F4` cycles these options. The default is `4` because lower surfaces appear only through holes/open space and therefore do not clutter ordinary solid terrain.

This supports readable:

- pits;
- shafts;
- deep cliffs;
- openings between levels;
- cave voids with lower floors.

The renderer does not draw multiple lower surfaces in one XY column. It draws the **nearest visible lower surface** because any nearer terrain closes the sight line.

## No normal ghost-above layer

Normal gameplay/debug view deliberately does **not** overlay the complete `Z+1` floor as transparency.

Showing two similar grass/floor textures simultaneously makes both levels harder to read. Upper structure is instead represented by what actually intersects the selected horizontal cut:

```text
terrain body at selected Z -> visible solid material
vertical connector          -> connector-specific presentation cue
upper floor that does not intersect the cut -> not drawn
```

A future construction/debug X-ray may deliberately show adjacent layers, but it is a separate presentation mode rather than the normal Z language.

## Mountains and caves

The slice contract makes mountains and underground space use the same rules.

A stacked mountain:

```text
terrain Z=3        ██ summit body
terrain Z=2      ██████
terrain Z=1    █████████
terrain Z=0  █████████████
```

appears as progressively different solid footprints when PageUp/PageDown moves the cut.

A cave is simply an open region inside a body layer while lower terrain remains as floor:

```text
selected Z=1

████████████████   terrain body at Z=1
██              ██
██    cave      ██   no body at Z=1
██              ██   support terrain at Z=0 becomes floor
████████████████
```

No separate `CaveShape`, `MountainShape` or visual-only simulation state is required.

A future ceiling/covered indicator may be useful for interior gameplay, but the current renderer intentionally does not infer entity-height or roof semantics that the simulation has not defined yet.

## Procedural visual contract

Current generated presentation is split by meaning:

```text
SimulationView
    ↓
LandscapeSliceResolver
    ↓ horizontal-cut role
LandscapeRenderer
    ├── surface role -> ProceduralLandscapePack
    └── cut-body role -> ProceduralSliceArt
```

`LandscapeTopology` supplies normalized 8-neighbour topology and deterministic XYZ visual variants to both generated-art paths.

Simulation still owns only what exists and how it behaves. Presentation owns pixels, palette, shading and derived visual cues.

### Native pixel profile

```text
logical world cell = 1 x 1 simulation unit
native visual cell = 16 x 16 source pixels
```

The 16-pixel value is presentation-only. Zoom changes screen size without changing simulation coordinates.

### Palette

`EvoForgePalette` contains the shared grass/earth language used by surface, cliff and cut-body generation. Restrained highlight/shadow/outline rules keep independently generated tiles coherent.

### In-memory atlases

Generated art is created from libGDX `Pixmap`s during visualizer startup and converted to `TextureRegion`s using `Nearest` filtering and one-pixel duplicate padding.

No source PNG, JSON visual descriptor, TexturePacker step or third-party asset installation is required.

## Cell-aligned topology

For terrain art the renderer observes eight neighbours:

```text
NW  N  NE
 W  C   E
SW  S  SE
```

`LandscapeTopology` uses an 8-bit mask with diagonal corner gating: a diagonal contributes only when both adjacent cardinal neighbours exist.

The same topology concept is used differently depending on the slice role:

- current/lower surfaces generate grass edges and exposed earth lips;
- solid-body cells generate earth/rock cut boundaries around open space such as cave walls;
- arbitrary plateau and cave outlines remain aligned exactly to simulation cells.

Four deterministic XYZ-selected variants reduce obvious repetition without frame-to-frame randomness.

## Ramp presentation across Z

Ramp semantics continue to come exclusively from `RampShape`.

The procedural surface pack generates four independently lit orientations:

```text
+X
-X
+Y
-Y
```

The horizontal-cut model gives the same authoritative Ramp several presentation views without creating duplicate simulation Shapes.

### Ramp on its supported standing plane

When the Ramp terrain is at `selected Z - 1`, the normal generated slope is shown.

### Ramp body intersecting the lower cut

When the Ramp terrain itself is anchored at `selected Z`, `ProceduralSliceArt` draws a directional ramp-cut pattern inside the solid material. This keeps the vertical connector readable when looking at the lower slice without pretending that the ramp is a walkable surface on that lower standing plane.

### Upper landing descent marker

On the Ramp's supported standing plane, the upper landing receives a small presentation-only descent mouth facing back toward the Ramp.

This marker is **derived** from the one authoritative RampShape. It is not another Shape, object or Navigation edge.

`F3` can still show explicit direction arrows for both current surface ramps and ramp bodies intersecting the selected cut.

## Rendering and debug UI

Terrain uses `SpriteBatch`. `ShapeRenderer` remains only for intentionally primitive/debug information such as objects, selection, grids and diagnostics.

Controls:

```text
Space          run / pause
N              one simulation tick while paused
PageUp/Down    move horizontal standing-Z cut
WASD           pan camera
mouse wheel    zoom
G              grid: off / subtle / debug
F2             Navigation transition overlay
F3             Ramp/Shape direction overlay
F4             lower visibility depth: 0 / 1 / 4
```

Click interaction always addresses `(x,y,selectedZ)`. A lower surface visible through a shaft does not silently become the clicked Z.

The inspector reports the resolved slice role (`SOLID BODY`, `SURFACE`, `LOWER depth N`, `EMPTY`), source terrain Z, Shape and outgoing transitions.

## Z stress / acceptance world

`VisualizerDemoWorld` is deterministic presentation-owned setup built through the real `SimulationAssembly`.

It now deliberately stresses the Z language instead of presenting only one plateau:

- broad lower meadow;
- irregular base plateau on standing `Z=1`;
- four real cardinal base ramps;
- mountain body stacked through several terrain Z levels;
- a west-facing cave entrance and chamber carved by absent body cells;
- cave floor supplied by the lower terrain layer;
- a high cliff with no special `CliffShape`;
- several higher local ramps forming a longer multi-Z ascent;
- summit reaching standing `Z=4`;
- one deep open shaft whose visible floor is several elevations below;
- slow and fast movers preserving the authoritative 2-tick / 8-tick Movement example.

Headless tests verify:

- all four base Ramp orientations;
- Ramp topology at successive mountain elevations;
- cave body absence plus real floor support;
- deep shaft gaps and lower floor;
- timed Movement behavior;
- slice priority and lower-depth clipping independently through `LandscapeSliceResolverTest`.

Manual acceptance should inspect the same XY area while switching through `Z=0..4`. The target is that the three-dimensional structure remains understandable without a transparent complete upper floor.

## Why external landscape search is frozen

Early external tileset experiments were useful for discovering the presentation boundary but repeatedly encoded a terrain grammar different from EvoForge's arbitrary Z topology.

For the current development phase, topology therefore generates its own canonical art. External or hand-authored art can still be introduced later behind the presentation boundary without changing simulation semantics.

## Deferred visual decisions

Documented but intentionally not implemented yet:

- ceiling/roof/covered-state presentation once simulation semantics require it;
- explicit adjacent-layer X-ray/build mode;
- additional materials: dirt, stone, sand, snow, water;
- priority/layered transitions between multiple materials;
- alternate procedural palettes/styles;
- larger anchored sprites for trees, creatures, buildings and equipment;
- external or hand-authored visual packs behind the same boundary;
- dual-grid / marching-squares selection for a future visual language that needs it;
- richer shadows/compositing;
- generated-atlas/export tooling;
- visual dirty caches/chunk render storage only after profiling.

The current renderer does not claim that every future art style must use the same autotiling algorithm. It establishes the first proven presentation semantics for EvoForge's Z world.

## Performance boundary

Renderer work remains limited to camera-visible XY cells. Slice resolution and topology are computed on demand from the existing sparse read contracts.

The current maximum lower-depth search is four additional terrain lookups per open XY column, not per ordinary solid cell. Measure real frame cost before introducing caches, packed keys or chunk-local render state.

## Next simulation consumers

The visualizer should remain an observer while the next simulation milestones arrive:

```text
Occupancy
    ↓
Pathfinder
    ↓
observable action outcome
    ↓
first agent / Cow vertical slice
```

Those systems may add diagnostics, but presentation stays non-authoritative.
