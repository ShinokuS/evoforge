# Z-level Visualizer and Procedural Landscape

The EvoForge visualizer is a **debug observer of the real simulation**, not a second world model and not an owner of simulation state.

Its current presentation contract is **full top-down**. Landscape art is generated by EvoForge itself at startup instead of depending on an external tileset.

## Module boundary

```text
simulation  pure Java, authoritative and headless
    ↑
core        libGDX presentation/debug visualizer
    ↑
lwjgl3      desktop launcher
```

`core` depends on `simulation`. `simulation` has no dependency back on libGDX, pixels, palettes, atlases or presentation code.

`SimulationAssembly` builds the initial world and `start()` returns `SimulationRuntime`. The visualizer receives only:

```text
SimulationView
SimulationTime
SimulationStepper
```

It never receives `SpatialSystem`, `TerrainSystem`, `GeometrySystem`, `MovementSystem`, `Scheduler` or `SimulationClock`.

## Z-plane meaning

Visualizer Z is the **standing/navigation plane**, because Spatial objects and Navigation transitions live at that coordinate.

Under the current supported-position Shape law, terrain/Shape supporting standing position `(x,y,z)` is read at:

```text
(x, y, z - 1)
```

The selected standing plane is authoritative. Optional lower context is presentation-only:

```text
selected Z:
    objects at Z
    support terrain/Shape at Z - 1

lower context:
    no objects
    dimmed support terrain from the immediately lower standing plane
    shown only where the selected plane has no supporting terrain at that XY
```

No positive/negative Z value is interpreted as inherently above-ground or underground.

## Procedural visual contract

The current landscape is generated entirely inside `core`:

```text
SimulationView
    ↓ terrain / Shape / XYZ
LandscapeRenderer
    ↓ neighbourhood + Z context
LandscapeTopology
    ↓ normalized cell topology
ProceduralLandscapePack
    ↓ generated TextureRegion
SpriteBatch
```

The important separation is:

```text
simulation       what exists and how it behaves
presentation     how that state is drawn
```

Simulation definitions contain no texture names, sprite ids or visual rules.

### Native pixel profile

The first EvoForge procedural profile uses:

```text
logical world cell = 1 x 1 simulation unit
native visual cell = 16 x 16 source pixels
```

The 16-pixel value is presentation-only. Zoom may display one world cell at more or fewer screen pixels without changing simulation coordinates.

### Palette

`EvoForgePalette` contains one restrained grass/earth palette. Generated tiles reuse the same base, highlight, shadow, deep-tone and outline colors so independently generated pieces stay visually coherent.

The palette is deliberately small. New materials should extend the visual language rather than introduce unrelated per-object color schemes.

### In-memory atlas

`ProceduralLandscapePack` creates one `Pixmap` atlas during visualizer startup, converts it to one libGDX `Texture`, then serves `TextureRegion`s from that texture.

No source PNG, JSON visual descriptor, TexturePacker step or third-party asset installation is required.

Generated regions use one-pixel duplicate padding around every 16x16 tile and `Nearest` filtering to keep pixel edges stable while zooming.

### Cell-aligned autotiling

Landscape remains aligned with the simulation grid.

For each terrain cell `LandscapeRenderer` observes the eight neighbours:

```text
NW  N  NE
 W  C   E
SW  S  SE
```

`LandscapeTopology` converts that neighbourhood to an 8-bit mask. Diagonals use corner gating: a diagonal contributes only when both adjacent cardinal neighbours exist.

This keeps:

- outer edges;
- outer corners;
- inner corners;
- arbitrary plateau outlines

expressible without moving the render grid half a cell away from the simulation grid.

The generator currently creates four deterministic visual variants for each topology. Cell XYZ selects a stable variant, so texture detail does not flicker between frames.

### Elevation edges

There is no `CliffShape` merely for graphics.

Exposed earth/cliff-looking edges are generated from the absence of same-level supporting terrain around the current surface. The visual edge is presentation-derived; authoritative vertical topology remains Terrain + Shape + Navigation.

North/west and south/east faces use different light/shadow treatment so elevation is readable in full top-down view without pseudo-isometric displacement.

### Ramp art

Ramp semantics continue to come exclusively from `RampShape`.

The procedural pack generates **four separate ramp orientations**:

```text
+X
-X
+Y
-Y
```

They are not produced by rotating one finished sprite. Geometry is symmetric, but lighting remains fixed in world space. This avoids rotating highlights and shadows together with the ramp.

Normal view should make ramp direction understandable from the generated terrain itself. `F3` remains an optional Shape-direction diagnostic overlay.

## Rendering and debug UI

World terrain is drawn through `SpriteBatch`. `ShapeRenderer` remains for deliberately primitive/debug information such as current object markers, selection and diagnostic arrows.

Controls:

```text
Space          run / pause
N              one simulation tick while paused
PageUp/Down    selected standing Z
WASD           pan camera
mouse wheel    zoom
G              grid: off / subtle / debug
F2             Navigation transition overlay
F3             Shape direction overlay
F4             lower-Z context
```

HUD information is rendered in opaque screen-space panels rather than bare text over the map. Cell inspection reports XYZ, support presence, Shape and outgoing transition count. Object inspection reports id, definition id and authoritative XYZ.

## Demo / acceptance world

`VisualizerDemoWorld` is presentation-owned deterministic setup content built through `SimulationAssembly`.

Current scene contains:

- a broad meadow on standing `Z=0`;
- an irregular plateau on standing `Z=1` to exercise ordinary edges plus inner/outer corner cases;
- one real Ramp on **each of the four plateau sides**;
- a small terrace on standing `Z=2`;
- another real Ramp connecting `Z=1` to `Z=2`;
- one slow and one fast mover on the main plateau.

The four first-level ramps are acceptance coverage for all cardinal orientations, not decorative copies. Headless tests verify their real Navigation transitions.

The second terrace proves that presentation is not hard-coded to a single elevation difference.

Both movers start an equal-cost adjacent `MoveStep` at tick zero. The fast mover completes after 2 ticks and the slow mover after 8 ticks, proving that presentation observes authoritative timed Movement rather than animating state independently.

## Why external landscape search is frozen

Early Minifantasy and Beast Pixels experiments were useful for discovering the required presentation boundary, but both also demonstrated the core mismatch: an external pack can easily lack a visual primitive for EvoForge's actual arbitrary Z topology or encode a different terrain grammar.

For the current development phase, landscape visuals therefore use the canonical procedural pack. This removes asset licensing/setup friction and lets topology dictate graphics rather than graphics dictate topology.

The presentation boundary still allows external or hand-authored art later. Procedural generation is the current canonical development visual language, not a new simulation dependency.

## Deferred visual decisions

The following ideas are recorded intentionally but are **not** implemented until a real consumer justifies them:

- additional procedural materials such as dirt, stone, sand, snow and water;
- priority/layered transitions between multiple terrain materials;
- alternate procedural palettes/styles;
- larger anchored sprites for trees, animals, buildings and equipment;
- external or hand-authored visual packs behind the same presentation boundary;
- dual-grid / marching-squares selector for a future pack that genuinely requires it;
- cached/dirty visual tiles or chunk presentation storage after measured renderer cost;
- multiple lower Z layers and stronger Z-fog/cutaway modes;
- generated-atlas/export tooling for art inspection outside the running visualizer;
- richer shadow/compositing passes;
- procedural characters/objects only when their first real gameplay consumer arrives.

Keeping these decisions documented instead of pre-implementing them preserves extension knowledge without creating dormant infrastructure.

## Performance boundary

Renderer iteration remains limited to the camera-visible XY range rather than scanning the whole object repository.

Terrain/Geometry reads deliberately remain on the existing sparse-storage path. Autotile topology is currently computed for visible cells rather than cached. JFR/representative world measurements must justify any dirty cache, chunk render storage or packed-coordinate optimization.

## Next simulation consumers

The visualizer should now be stable enough to observe the next simulation milestones:

```text
Occupancy
    ↓
Pathfinder
    ↓
observable action outcome
    ↓
first agent / Cow vertical slice
```

Those systems may add debug overlays, but each remains authoritative in its own simulation subsystem. Presentation stays an observer.
